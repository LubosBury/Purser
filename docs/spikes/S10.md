## Questions

| # | Question | Facts / rule |
|---|---|---|
| Q1 | An IAP already has manual prices. Does `POST /v1/inAppPurchasePriceSchedules` with a manual price list that leaves one territory out **replace** the whole schedule (the territory left out loses its manual price), **merge** with it (the territory keeps its old manual price), or **fail** (a 409 because a schedule exists)? | rule L1, S10 (`IAPScheduleSpikeGateRule`); `WriteBodies.replaceIAPSchedule`; FakeASC `postSchedule` replaces |
| Q1b | Does that POST also remove a **future** manual price (a start after today) it does not list? | rule L1 ("all manual prices including future ones"); `ImportTable.removedManualPrices` |
| Q1c | Does every POST create a new schedule id and new ids for every manual price row, or are the ids of unchanged rows kept? | FakeASC gives a new `sched-…` id and new row ids; verification matches rows by territory, point and start (`IAPScheduleSemantics`) |
| Q2 | A manual price sent with `startDate: null`: is it read back as `null` or as the creation day (today, UTC)? Does that change a day later? | FakeASC `iapNullStartEchoesCreationDay` (false); `IAPScheduleSemantics` counts a start on or before today as current; `TargetMatchingTests` |
| Q3 | Territories without a manual price (rule L2): do they show in `automaticPrices` with a price derived from the base territory; does a territory whose manual price was removed (Q1) come back there; does a change of the base price move them, and when (same request, minutes, next day)? Does a territory with a manual price also show in `automaticPrices`? | rule L2 (`IAPScheduleDiff.autoPricedTerritories`); `docs/research/asc-api-paths.md` (automaticPrices is only observed, the sync does not read it) |
| Q4 | A POST whose manual prices have no row for the base territory: refused (409, code and detail) or accepted? | rule L1, STRUCT block "no base price" (`PlanBuilder+Import`) |
| Q5 | Two schedule POSTs on the same UTC day, each with a `startDate: null` price for USA: accepted, and which one is in effect? | Purser may write a schedule and a corrected one the same day (replan) |

## Before the first step

1. Build the DEBUG app signed (`make build-signed`), open Juice, then **Sync** in the sidebar.
2. In Catalog, PurserSpikeLifetime: note its availability (USA, GBR and JPN must be available; if one is not, pick another available territory and use it everywhere below instead) and its current schedule (base territory, manual prices). Take a screenshot of its Pricing page in App Store Connect.
3. Open the Spike console (Window menu → Spike console), set Spike = `S10`. The console fills these variables from the catalog: `SPIKE_LIFETIME`, `SPIKE_SCHEDULE` (the schedule id, missing when the IAP has no schedule), `SPIKE_BASE` (its base territory), `PP_LIFE_<T>_LOW/MID/HIGH` (5th, 15th and 25th IAP price point of territory T, cheapest first), `MANUAL_LIFE_<T>` (the manual price row in effect today), `CURPP_LIFE_<T>` (its price point), `ABOVEPP_LIFE_<T>`, `SCHED_LIFE_<T>` (the first future manual price row). An unknown `{{…}}` stops the request before anything is sent.
4. Empty the Query field before every POST: a query left from a GET makes Apple answer 400 `PARAMETER_ERROR.ILLEGAL` (S10-6, first attempt). Put these lines into the console's Variables field and keep them for the whole spike (each step below adds or changes only the lines it names):

```
IAP={{SPIKE_LIFETIME}}
BASE=USA
```

The three POST templates are in `docs/spikes/bodies/` ("Load template…"): `s10-iap-schedule-two-now.json` (two manual prices, `startDate: null`), `s10-iap-schedule-now-and-future.json` (one from today until `{{START}}`, one starting `{{START}}`; the first row needs `endDate: {{START}}`, see S10-6) and `s10-iap-schedule-one-now.json` (one manual price, `startDate: null`). Each takes `IAP`, `BASE`, `LP_1` and, where present, `LP_2` and `START`. `BASE=USA` is fixed on purpose: if S10-1 shows another base territory, S10-3 also moves the base to USA; write that down.

**Sync after every POST, before the next GET.** The sync refreshes `SPIKE_SCHEDULE`, `MANUAL_LIFE_*` and `SCHED_LIFE_*`, and only a schedule id the sync has read can be read by id (AppGuard). If the schedule id changed (Q1c), the GETs by `{{SPIKE_SCHEDULE}}` follow it after the sync.

Standard queries, used by the steps below:

- *manual*: GET `/v1/inAppPurchasePriceSchedules/{{SPIKE_SCHEDULE}}/manualPrices`, `include=inAppPurchasePricePoint,territory&limit=200`
- *automatic*: GET `/v1/inAppPurchasePriceSchedules/{{SPIKE_SCHEDULE}}/automaticPrices`, `include=inAppPurchasePricePoint,territory&filter[territory]=USA,GBR,JPN&limit=200`

## Conclusions

| Question | Answer | Confidence (H/M/L) |
|---|---|---|
| Q1 | **Replace.** A POST on an IAP with manual prices is accepted (201) and the schedule becomes exactly the body: GBR, left out, lost its manual price (S10-6r2, S10-7) | H |
| Q1b | **Replace, future rows included.** The 2026-11-15 USA row, left out, is gone (S10-9, S10-10) | H |
| Q1c | The schedule id stays the IAP id on every POST. A row id is derived from its content (IAP, territory, point, start, end): an unchanged row keeps its id, a changed row (another end date) gets a new one; an identical POST changes nothing (S10-12) | H |
| Q2 | Same day: `startDate: null` is returned as `null`, in the POST response and in the read (S10-3, S10-4). The next day: pending (S10-14) | M |
| Q3 | A territory without a manual price is in `automaticPrices` (`manual: false`), derived from the base at once, with the base's intervals (future change included). A territory with a manual price is only in `manualPrices`; the lists do not overlap. Removing a manual price moves the territory to the derived price in the same request (GBR £1.29 → £0.99), so a removal changes what its customers pay (L2 WARN is right). A change of the base price moves every derived territory in the same request (S10-5, S10-8, S10-11) | H |
| Q4 | **Refused**: 409 `ENTITY_ERROR.BASE_TERRITORY_INTERVAL_REQUIRED` (S10-12r) | H |
| Q5 | Several schedule POSTs the same UTC day (four 201s: S10-3, S10-6r2, S10-9, S10-12), each with a `startDate: null` USA price, are accepted; the last one is in effect | H |
| Extra | Overlapping intervals in one territory are refused: 409 `ENTITY_ERROR.INVALID_INTERVAL` (S10-6, 08:38); a current row before a future one must end on the future start | H |

## Effect on the code

- AppleConstants: `iapScheduleReplaceConfirmed` false → true in Purser 1.3.0 (Q1 and Q1b "replace"); the tests in `IAPScheduleScenarioTests` gated on it run, the S10/S10a ones are skipped, and exception S10a no longer applies.
- FakeASC `postSchedule`: keep the schedule id (Apple keeps the IAP id) instead of a new `sched-…` id on every POST; derive row ids from territory, point, start and end; refuse overlapping intervals with 409 `ENTITY_ERROR.INVALID_INTERVAL` and a schedule without a base-territory row with 409 `ENTITY_ERROR.BASE_TERRITORY_INTERVAL_REQUIRED` (fixtures above). Not changed yet.
- FakeASC `iapNullStartEchoesCreationDay`: false confirmed for the same day; final after S10-14
- `IAPScheduleSemantics` / verification: no change (starts come back as sent)
- Rule L2 (`IAPScheduleDiff`, the IAP plan screen hint): no change; Apple's derived prices follow at once. Reading `automaticPrices` in the sync stays out of v1
- README (the S10 paragraph) and the spec rows L1, L2, S10, after the constant changes
- Contracts: none
